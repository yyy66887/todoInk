# 0001：先建立单模块开发 Harness

- 状态：ACCEPTED（本次 harness 的实施选择）
- 日期：2026-09-20
- 关联：[HARNESS-001](../tasks/HARNESS-001.md)
- 修订：用户指出缺少 AI 自动发现入口后，按 [HARNESS-002](../tasks/HARNESS-002-agent-entry.md) 调整第 1、6 项；其余取舍保留。

## 问题与依据

用户要求借鉴 DBX 开发模式，在 TodoInk 的 `doc` 目录建立 harness。现有 Android 项目已具备通知采集骨架，未见测试与 CI，源码行为与 README 存在差距。DBX 材料 §13.9 建议优先交付规则入口、任务记录、检查入口、验证与交接。

## 决策

1. 详细交付位于 `doc`，包括参考资料快照、文档、模板、任务与 PowerShell 检查脚本；根目录增加简短 AGENTS.md 作为 AI 开发入口。
2. 保持 Kotlin / Compose / Room / Hilt 和单 `:app` 模块；使用包级约束与精确历史例外。
3. Kotlin 类型与 Room schema 保持事实来源，不引入缺乏真实使用方的描述语言和代码生成器。
4. 首版检查文档、源码引用与契约文件可读性；提供 Gradle 包装入口，严格拒绝没有测试证据的绿色结果。
5. 应用缺陷只登记与准备任务，不在搭建 harness 时顺带修复。下次功能任务先引入必要测试。
6. 根 AGENTS.md 引导助手读取 harness，避免每次依赖使用者显式指路。暂不添加 CI workflow 或自动执行器；接入 CI 后沿用同一脚本。

## 替代与取舍

仅写一份建议文档反馈太弱，因而附带可执行结构检查；直接迁移完整 DBX 框架会超出当前产品规模。轻量引用扫描成本低，但不等价于编译器 / 依赖图分析，局限在架构文档中公开。

## 重审条件

第二个用例共享契约、新增生产源集 / 模块、CI 耗时显著增长、引入固件 / 网络、持续自动执行需求出现时重审。新任务的授权与需求优先于参考材料中的未来建议。
