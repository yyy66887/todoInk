# NI-002：建立稳定且原子的快照去重

- 状态：READY（2026-09-20 Phase 1 v0.1 获批，见方案第 9 节审核记录）。
- 里程碑：M2；优先级：P0；依赖：NI-003、NI-000。
- 契约：C04、C05、C12；场景：V03、V04、涉及变更的 V13。

## 当前问题与目标

现有哈希包含 postTime，未覆盖结构化消息；查询最新记录和保存不在同一个数据库事务内。目标是同 key 内容未变只累加观察次数、内容变更形成连续版本、多个合法写入口并发时结果仍一致。

## 范围与步骤

1. 以 NI-003 的字段清单定义确定性哈希输入与编码，排除 postTime / receivedAt 这类观察时间。原始消息自身时间与结构是否构成语义变化要明确，不与通知投递时间混淆。
2. 在 Repository / DAO 事务边界内完成查最新、比较、计数或新增；不依赖所有调用者都持 Recorder 的锁。
3. 测试重复、更新、恢复旧正文与不同 key，不将快照去重升级为猜测消息身份的跨通知合并。
4. 处理旧哈希算法兼容。需要重算或新增版本标识时有明确迁移；不能无记录地重写历史，也不把不可回补字段假装存在。

主要位置：NotificationRepository、NotificationSnapshotDao、必要的 schema / migration 与生产行为测试。字段表示变动需同步 NI-003 和 CONTRACTS。

## 验收

| 场景 | 预期结果 | 状态 |
| --- | --- | --- |
| 同 key 同内容重复 N 次 | 一份当前内容版本，observeCount 累加正确 | NOT_RUN |
| 仅 postTime / receivedAt 变化 | 不产生新内容版本 | NOT_RUN |
| 同 key A→B→A | 三个连续内容版本 | NOT_RUN |
| 只改变 MessagingStyle 有效正文 | 保留新内容版本 | NOT_RUN |
| 不同 key 相同文字 | 两个独立通知，不合并 | NOT_RUN |
| 多个协程并发提交相同内容 / 更新 | 无重复版本、无丢失计数，提交顺序可解释 | NOT_RUN |
| 旧记录升级后再收到同通知 | 兼容行为符合记录的策略，不静默丢历史 | NOT_RUN |

Verify + 真实 Room 集成用例；观察数据库最终状态，不能用只会顺序返回的假 DAO 证明事务正确。失败时不直接无限重试写操作。
