# NI-004：队列、异常与取消可观察

- 状态：READY（2026-09-20 Phase 1 v0.1 获批，见方案第 9 节审核记录）。
- 里程碑：M3；优先级：P0；依赖：NI-000、NI-001；最终联测需 NI-002 / NI-003。
- 契约：C03、C08、C09、C11；场景：V07、V09。

## 当前问题与目标

队列使用 DROP_OLDEST，但失败记录只关注 trySend；通用异常捕获可能掩盖取消。目标是每次丢弃、保存失败和取消都有正确语义，单条故障不让后续采集停止，回调不阻塞。

## 范围与步骤

- 明确队列容量与溢出策略，保留有界内存；为实际被丢项建立可观察计数，不只统计发送失败。
- 区分来源拒绝、队列丢弃、解析不支持、保存失败和取消。状态只记录错误码与必要诊断，避免正文和异常详情泄漏。
- 在所有相关协程边界传播取消，不仅修复 Recorder，也核对 Registry 等会捕获异常的路径。
- 注入可控调度与存储故障，证明后续合法通知仍可处理；未知提交结果不自动重放。
- 通过状态存储和已有状态页展示计数 / 最近错误，不重新创建第二套采集服务。

范围：NotificationRecorder、ParserRegistry、ListenerStatusStore、相关状态 UI 与回归。调整存储事务仍由 NI-002 承担。

## 验收

| 场景 | 预期结果 | 状态 |
| --- | --- | --- |
| 正常处理 100 条不同 key 合成通知，无溢出 / 取消 / 存储故障 | 最终 100 条保存，计数一致 | NOT_RUN |
| 冻结消费者，容量填满后继续投递 | 被丢项与计数一致、内存有界、状态可见 | NOT_RUN |
| 一条解析抛错、一条存储失败，随后正常通知 | 错误可解释，后续仍处理 | NOT_RUN |
| 处理过程中取消 | 取消向上传播，不报 save_failed、不重放 | NOT_RUN |
| 重连补采重复通知 | 仍经过相同来源检查与幂等持久化 | NOT_RUN |

Verify + 可控并发 / Room 联测；适用设备行为执行 Device。不能用增加延时碰运气测试竞态，也不为追求“零丢失”改成无界队列。
